# STS2 BI Modelling

## 🎯 Overview

This project analyses performance in Slay the Spire 2 using run-level JSON
data, and doubles as a showcase of BI engineering practices: data
modelling (star schema), storage/query design (partitioning, clustering,
incremental dimensions), an automated ingestion pipeline, and dashboard
performance decisions in Power BI.

The goal is to understand:

* What drives win rate
* How runs evolve over time
* Which decisions impact outcomes

---

## 🏗️ Architecture

```
Local .run files (game saves)
        │  scripts/upload_to_gcs.py  (Task Scheduler, monthly)
        ▼
GCS bucket (raw landing zone)
        │  cloud_function/  (triggered on new object: flatten + load)
        ▼
BigQuery  sts2          raw landing tables (sql/schema.sql)
        │  dbt build    (GitHub Actions, daily, keyless auth)
        ▼
BigQuery  sts2_staging  1:1 cleaned views
        ▼
BigQuery  sts2_marts    tested, contract-enforced star schema
        │  Import mode
        ▼
Power BI  (powerbi/ PBIP project, reads sts2_marts only)

Second source: the installed game files (SlayTheSpire2.pck, sts2.dll)
        │  scripts/build_reference_seeds.py  -> dbt seeds (cards, events,
        │                                       relics, Ancient dialogue)
        │  scripts/extract_event_images.py   -> local artwork + palettes
```

* **Ingestion**: a local script uploads new `.run` files to a GCS bucket,
  tracked via a local manifest so re-runs only pick up new files.
* **Flatten + load**: a GCS-triggered Cloud Function flattens each run's
  nested JSON into relational landing tables in BigQuery (`sts2`),
  replacing any existing rows for that run_id (idempotent, safe to
  re-trigger). Partitioned by run date and clustered for common filters;
  see `sql/schema.sql` for the reasoning.
* **Transform + test**: dbt (`dbt/`) builds staging views and the marts
  star schema, and runs every data-quality test. It runs daily in GitHub
  Actions, authenticating to GCP via Workload Identity Federation (no
  service-account key exists anywhere). A failed test fails the run.
* **BI layer**: Power BI in Import mode, reading only `sts2_marts`. The
  semantic model is checked in as a PBIP project (`powerbi/`). See
  `docs/powerbi_setup.md`.

Setup guides: [`docs/gcp_setup.md`](docs/gcp_setup.md) for provisioning
GCP, [`docs/powerbi_setup.md`](docs/powerbi_setup.md) for connecting and
modelling in Power BI. Current build status, deployed resource names, and
issues hit along the way are tracked in [`docs/progress.md`](docs/progress.md).

**The full story** (every stage, each problem hit, how it was solved and
why, and the lessons) is in [`docs/lessons_learned.md`](docs/lessons_learned.md).

## 📊 Data Source

Data comes from local `.run` files generated by the game (JSON, one file
per run). Each file contains player data, map progression, and events/
outcomes. Raw data is not included in this repository.

Reference data (card pools, rarity, type and cost; event, option and relic
names and text) is read from the player's **own game install** by
`scripts/build_reference_seeds.py` and committed as dbt seeds. An
earlier version scraped a fan wiki. That was replaced after its terms
were found to forbid automated collection, and the game's own files
are the more authoritative source anyway. Event artwork is extracted
the same way (`scripts/extract_event_images.py`) but stays local
(gitignored), since the images are Mega Crit's to distribute, not ours.

## 🧱 Data Model

The star schema Power BI reads lives in `sts2_marts`, built by dbt:

**Dimensions**
* `dim_run`: one row per run, and the hub every fact relates to.
  Run attributes (character, ascension, mode, outcome, killed by) plus
  derived run metrics: `floors_reached`, `acts_reached`, `death_floor`,
  `player_count`, and single-player `final_hp` / `total_damage_taken`
* `dim_card` / `dim_relic`: catalogs discovered from the data, enriched
  from the game files (card pool, rarity, type, cost, colour; relic names)
* `dim_event`: every event and Ancient seen in runs, with its opening text
* `dim_ancient_dialogue`: what each Ancient says to each character, by
  encounter
* `dim_date`: calendar for time intelligence, generated in dbt

**Facts** (each relates to `dim_run` on `run_id`, never to another fact)
* `fct_floor_state`: one row per run/floor/player, HP and gold over time
* `fct_card_choice`: one row per card offered at a choice screen, with
  `was_picked`; drives pick-rate and decision-impact analysis
* `fct_card_gained`: cards added outside a choice screen
* `fct_card_run`: card offers rolled up to run / player / card (picked vs
  skipped in the same run, for the win-rate comparison)
* `fct_event_choice`: one row per event or Ancient choice, joined to what
  happened next (died before the next act, within 3 floors, HP/gold change)
* `fct_combat`: one row per fight per player: encounter, turns, HP going
  in, damage as a share of max HP, potions drunk, and whether the run was
  lost right there; `dim_encounter` adds names and the game's death lines
* `fct_rest_choice`: every rest-site choice (rest, smith, relic options)
  with HP going in and whether the run died before the next act
* `fct_potion_event`: one row per potion offered / drunk / discarded /
  bought on a floor; `fct_potion_run` rolls it up per run, player and
  potion, incl. potions still held when the run ended
* `fct_run_relic` / `fct_run_deck_card`: end-of-run relic and deck snapshots

Grain, column descriptions and contracts are in
`dbt/models/marts/_marts__models.yml`. The raw landing tables and their
partitioning/clustering rationale are in `sql/schema.sql`.

**Where logic lives:** row-level derivations (floors reached, death floor,
names) are computed in dbt, where they're tested and reusable by any tool.
Aggregations (Win Rate, Card Pick Rate) are DAX measures in the Power BI
semantic model.

## ✅ Data Quality

`dbt build` runs every check below on every build (all pass, except 1
expected warning for 3 cards the game has since retired):

* **Source tests on the raw tables** (strict): unique/not-null keys. These
  exist because of a real incident: concurrent Cloud Function invocations
  raced the `dim_card` MERGE and inserted 38 duplicate card IDs, which
  only surfaced when Power BI refused to load the relationship. A `unique`
  test catches that the same day. (Root cause fixed with
  `--max-instances=1`; see `docs/gcp_setup.md`.)
* **Referential integrity**: every fact's `run_id` exists in `dim_run`,
  every `card_id`/`relic_id` exists in its catalog, and every run date
  exists in `dim_date`.
* **Contracts** on all marts, so a column or type change fails the build
  instead of silently breaking the report.
* **Singular tests** (`dbt/tests/`): floor-state grain is unique, HP stays
  within `[0, max_hp]`, `run_date` matches the `run_id` timestamp, and every
  run has floor data (except runs abandoned within a minute).

Findings the modelling surfaced:
* The raw `acts_completed` is always 3. It's the number of acts on the
  map, not progress, so a "floors reached" metric built on it was wrong.
  `dim_run` derives real `floors_reached` / `acts_reached` from floor states.
* 25% of runs (234/946) are multiplayer, where the host player isn't
  identifiable, so per-player HP metrics are only filled for
  single-player runs instead of guessing.

## 🚧 Current Scope

* Co-op runs are real and queryable — `player_id` (a genuine Steam64 ID
  in multiplayer runs, confirmed against real data with up to 4 distinct
  players in one run) is carried on every relevant fact table, so
  teammates' decks/relics/floor state can be compared directly
* `fact_run.character` only extracts `players[0]` — non-host players'
  character choices aren't captured anywhere yet
* Run modifiers and card upgrades/removals are in the raw JSON but not
  modelled yet (see `docs/roadmap.md`)
* Event artwork is not in the repo: run `scripts/extract_event_images.py`
  against your own install to see it (the report works without it)

## 📑 Report & audit

* Report pages: **Where runs end**, **Fights & rest sites** (death rate
  per encounter and by HP going in: bosses entered under 40% HP kill 29%
  of the time vs 8% above 70%), **Solo vs Multiplayer**, **Cards**,
  **Events** (pick an event and the page takes on its artwork and colours;
  option outcomes, and Ancient dialogue by character and encounter),
  **Potions** (pick and drink rates, picked-vs-skipped win rates, and how
  often runs are lost with potions unused: 42% of losses) and **Explore**.
  Every page is dark and themed by the Character slicer (that character's
  artwork and colour).
* [`docs/report.pdf`](docs/report.pdf): static export of the Power BI report,
  viewable without Power BI (exported before the Events page was added).
* [`docs/audit.pdf`](docs/audit.pdf) ([markdown](docs/audit.md)): evidence-based
  end-to-end audit from local save files to the report. Covers the
  reconciliation chain (946 runs at every stage), status by stage, and a
  prioritised findings register.
